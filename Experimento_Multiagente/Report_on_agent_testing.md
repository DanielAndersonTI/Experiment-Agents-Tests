# Report on Agent Testing — Starting Point

## 1. Project Context

This project replicates and extends the study *"Toward Generating Microservice Architectures from Textual Requirements with LLMs"* (SBCARS 2025), which used Zero-Shot and Few-Shot prompts with GPT-4 to generate microservice architectures. Our extension replaces prompts with an **AI agent pipeline** orchestrated with **CrewAI + LangChain**.

**Studied systems:** PetClinic (7 services) and Bookstore (9 services).  
**Metrics:** Precision, Recall, F1 for services (RQ1) and interactions (RQ2).

---

## 2. Experiment Timeline

### Phase 1 — Environment Setup
- Folder structure created
- Base notebook with imports and configuration
- `requirements.txt` with dependencies (CrewAI, LangChain, Google Generative AI)
- `.env.example` template for API key

### Phase 2 — First Agent (Software Architect — DDD)
- Implemented **Agent A** with `role="Software Architect"`, using a DDD approach
- Output in CSV format: `Microservice, Responsibilities, Communicates With`
- Usage of `backstory` and `memory=True` to specialize the agent
- Initially tested with OpenAI, then migrated to Google Gemini

### Phase 3 — Second Agent (Alternative Architect — Event-Driven)
- Implemented **Agent B** with an alternative approach (event-driven, focused on scalability)
- Same task, different perspectives
- Generates independent proposals for comparison by the validator

### Phase 4 — Validator Agent and Consolidation
- Implemented **Agent 3 (Validator)** to compare and consolidate both proposals
- Initial version: symmetric consolidation
- Improved version: **asymmetric consolidation** — adopts services from Agent A as a baseline and only adds items from Agent B when there is consensus or clear justification in the requirements

### Phase 5 — Automatic Evaluation
- CSV parsing into service and interaction structures
- Comparison against reference architectures (`petclinic_ref.dot`, `bookstore_ref.dot`)
- Calculation of Precision, Recall, and F1 for services and interactions
- Saving results in `result/<system>/run_<timestamp>/` with CSV and JSON files

---

## 3. Problems Faced and Solutions

| Problem | Solution |
|----------|---------|
| Zero metrics due to unmapped service names | Created synonym dictionaries (`PETCLINIC_NAME_MAP`, `BOOKSTORE_NAME_MAP`) |
| Parser captured decision text as services | Added filters to ignore lines `===`, `- `, `--`, `**`, `#` |
| Agent A omitted infrastructure services | Reinforced the agent's `goal` and `task` instructions |
| Gemini API quota exceeded (429 error) | Changed model to `gemini-2.0-flash` (separate quota); both quotas were exhausted on the same day |
| Space in model name inside `.env` | Fixed by removing spaces |
| Validator discarded correct interactions from Agent A | Implemented asymmetric consolidation |

---

## 5. Lessons Learned

1. **Agent backstory matters**: A well-defined `backstory` significantly improves the quality of LLM responses
2. **Asymmetric consolidation is superior**: The validator should not discard correct services generated by the DDD agent during consolidation
3. **Synonym mapping is essential**: Service names vary between executions and require normalization
4. **Free models have limitations**: Gemini's quota is insufficient for multiple consecutive executions
5. **CSV as output format**: Structured, easy to parse, and suitable for automatic comparison
6. **Model variability**: Gemini presents variation in interaction results, affecting average performance but not peak performance

## 6. Current State and Next Step

The current pipeline has **3 agents** (Architect A, Architect B, Validator).  
The code is functional for PetClinic and Bookstore, in both Zero-Shot and Few-Shot modes.

**From this point forward**, we will evolve to **4 agents**:
- 3 agents will execute architecture generation tasks
- 1 agent will perform evaluation and selection of the final system

This report marks the starting point for this new phase.

## LLM Model Configuration Update

As a step to validate the agent infrastructure, we replaced the direct dependency on the Google Gemini API with **OpenRouter**, which acts as a unified access layer for multiple language models. This change allows testing different LLMs without significant modifications to the system architecture. For the initial tests, the **DeepSeek Chat V3 (`deepseek/deepseek-chat-v3-0324`)** model was selected and configured through an OpenRouter API key. This approach facilitates future comparisons between models such as DeepSeek, Gemini, Qwen, and Llama, while maintaining the same agent implementation and only changing the provider and model identifier.

## Test 8 - OpenRouter/DeepSeek Integration and Initial Agent Evaluation

In this stage, the language model configuration was successfully migrated from Google Gemini to **DeepSeek Chat V3 via OpenRouter**, allowing the continuation of experiments with a new LLM access infrastructure. After validating the API communication, **Test 8** was executed using the Few-Shot strategy with the three proposed agents (Software Architect, Alternative Software Architect, and Architecture Validator), validating the complete pipeline for architecture generation, consolidation, and evaluation.

In the **Bookstore** system, used as the main experimental challenge, Agent 1 (Software Architect) achieved maximum performance, reaching **Precision = 1.00, Recall = 1.00, and F1-Score = 1.00**, while the consolidated architecture achieved **Precision = 0.875, Recall = 1.00, and F1-Score = 0.9333**. The results indicate that DDD-based decomposition has a high capability for identifying business services; however, the consolidation stage still introduces additional elements that may reduce precision.

Therefore, the next experiments will primarily focus on improving **Agent 2 (Alternative Software Architect)**, as we believe that adjustments to its behavior, generation criteria, and service inclusion control mechanisms can increase the quality of alternative proposals and consequently improve the quality of the data used by the validator agent and the consolidated architecture. Initially, the focus will be on experiments using the **Bookstore** system.
